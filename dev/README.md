# dev/

Development-only fixtures and preview output. Nothing here is ever part of the production build,
and nothing here may contain real facts about real temples — see the guardrails below.

## `dev/fixtures/`

`sources.json`, `temples.json`, `timeline.json`, `glossary.json`, `elements.json`, `academy.json`
and `media.json` mirror the real `data/*.json` schema exactly, but every string is obviously fake
("FIXTURE Temple A", "Lorem ipsum…", source ids like `fixture-source-1` pointing at
`https://example.org/...`). They exist so components can be built and QA'd before real research
data lands, and so the build script and every shared component have a fast, deterministic input to
test against.

`dev/fixtures/assets/` holds two tiny real SVG files (a generic mark and a hero build-up line
drawing with the required `layer-*` group ids) so the figure/hero components have something real to
inline when previewing — these are placeholders for the eventual Gemini-generated assets in `img/`,
not production art.

Coverage in the fixtures: all three evidence tiers, a `null` fact (renders "Not yet verified"), a
`uncertain` ("Debated") claim with a `note`, a `catalogue-only` claim with `human_approved` set (the
"source not viewable online" marker), and media assets in every status (`approved`, `delivered`,
`placeholder`, `rejected`), plus a CC-licensed photo credit.

## `dev/preview/`

Build output only — generated by `node scripts/build.mjs --data dev/fixtures --out dev/preview`.
Not committed content in the same sense as the real site; regenerate it any time.

`dev/preview/components.html` is a single-page gallery exercising every shared component (evidence
badges + tooltips, claims + citations + sources list, figures in every media status, buttons,
cards, the native `<details>` accordion, the info panel dialog with focus management, and the
hotspot pattern) — use it to QA a component change without needing real content.

## Guardrails

- `scripts/build.mjs` refuses to build `--data dev/fixtures` (or any path under it) to anywhere
  outside `dev/` — there is no way to make fixture content land in the production build by
  accident.
- The content validator (`node scripts/validate-content.mjs`) only ever looks at `data/`, never at
  `dev/`, so fixtures are free to violate schema fine print if that's useful for a component demo
  (e.g. a media `path` that points at `dev/fixtures/assets/...` instead of `img/...`, purely so the
  SVG-inlining code has a real file to read without touching `img/`, which is the asset-integrator's
  lane).
- Never copy fixture text into `data/*.json` — the validator blocks the literal word "FIXTURE",
  "lorem ipsum", "TODO" and "TBD" in real data as a second line of defence.

## Rebuilding the preview

```bash
node scripts/build.mjs --data dev/fixtures --out dev/preview
```
